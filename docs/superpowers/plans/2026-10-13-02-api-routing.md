# DengueSense /v1 API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `/v1` REST surface that the iOS ward-capture app needs: auth, RBAC, idempotency, patient lookup, consent, scans, artefact uploads, clinical data, review, devices and audit. It also emits an OpenAPI contract for the iOS client.

**Architecture:** A Fastify 5 app in `backend/src/` built by `buildApp(deps)`. Every external system sits behind an injected interface (JWT keys, object store, quality queue, App Attest verifier, WebAuthn verifier, push sender), so tests use fakes. Each request runs its SQL inside `withRls()`, which sets the `app.*` settings that plan 01's RLS reads. Every mutation writes its audit row in the same transaction.

**Tech Stack:** Node 22, TypeScript, Fastify 5, `zod` + `fastify-type-provider-zod`, `@fastify/swagger`, `jose`, `pg`, `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, `@simplewebauthn/server`, Vitest, `@apidevtools/swagger-parser`.

**Spec:** `docs/superpowers/specs/2026-10-13-ios-ward-capture-app-design.md` (§6, §8, §11, §16, §16a), with `04-api-reference.md`.

**Depends on:** plan `2026-10-13-01-database-schema.md` (all tasks). Reuse `getTestPool`/`asRole`, the fixtures and the tables from it.

## Global Constraints
- All routes live under `/v1`. JSON bodies are validated by zod; unknown fields are rejected with 400 (doc 04 §5 minimisation).
- Error envelope, always: `{"error":{"code","message","detail","request_id","trace_id","timestamp"}}`. Clients dispatch on `code`.
- Every POST needs an `Idempotency-Key` (UUID v4). If it's missing: 400 `DS_IDEMPOTENCY_002`. Same key with the same payload hash replays the stored response. Same key with a different payload: 409 `DS_IDEMPOTENCY_001`. Keys are kept for 24 h.
- An RBAC denial on a resource lookup returns **404**, never 403 (doc 04 §3.8). A role not allowed on the route at all returns 403.
- Responses never include direct identifiers (name, NRIC, MRN, DOB).
- If the audit insert fails, the whole transaction rolls back and the response is 403 `DS_AUD_001`.
- Access JWT: RS256, 15 min; claims `sub, roles, site_id, deidentify, jti`. Device token: `aud = "device-upload"`, claims `device_id, site_id`, TTL 24 h. It may only call artefact routes and `GET /v1/scans/:id`.
- Pre-signed part URL TTL is 900 s. The 30-min duplicate-scan rule compares the new `captured_at` with the latest existing `captured_at` for that patient.
- No route exposes a risk score; `POST /assessments` is **not** implemented in Phase A.

## Review Focus
1. **Two identical POSTs sent at the same time** (a mobile retry race) create one scan, not two. The test fires two parallel `POST /scans` with the same key and expects one row and two identical responses (Task 3).
2. **A device token used on a patient route** (`GET /patients/lookup`) is rejected with 403. The test is in Task 2.
3. **An offline capture uploaded after the patient's consent was withdrawn** gets 451 `DS_REG_001`, and a `capture_rejected_post_hoc` audit row is written. The test is in Task 5.
4. **A complete call whose sha256 doesn't match the stored object** marks the artefact `rejected` and returns 422 `DS_UPLOAD_001`, with no `received_verified`. The test is in Task 6.
5. **Expired consent snapshot plus a superseded version** returns 451 `DS_REG_002`, not 422. The test is in Task 5.

### Task 5: Scans and per-step recapture

**Files:** Create `backend/src/routes/scans.ts`, `backend/src/consentGate.ts`, `backend/test/api/scans.test.ts`

**Interfaces:**
- `POST /v1/scans` (`nurse_operator`, `clinician`) takes:
  - `{ client_session_id: uuid, patient_id: uuid, captured_at: datetime, offline: boolean, protocol_version: string, capture_steps: ('neutral_face'|'fingertip_ppg'|'ocular_capture'|'dorsal_tongue')[], device_attempts: { step, attempt (1-3), device_verdict, reason_codes[] }[], metadata: CaptureMetadata }`
  - `CaptureMetadata` holds doc 03 `ContextualMetadata` plus `mount: 'handheld'|'holder'`, `lighting_type`, `exposure_duration_ms`.
- Responses:
  - 201 → `{ scan: { id, status, client_session_id } }`
  - The same `client_session_id` again → 200 with the existing scan
- Order of rules:
  1. Consent invalid: withdrawn → 451 `DS_REG_001`; superseded version → 451 `DS_REG_002`; no primary_research → 451 `DS_REG_001`. If `offline=true`, also write a `capture_rejected_post_hoc` audit row.
  2. Another scan for the patient whose `captured_at` is within 30 min → 409 `DS_SCAN_001`.
  3. Insert the scan and attempts, and audit `scan:create`.
- `GET /v1/scans/:id` returns `{ scan: { id, status, steps: [{ step, attempt, device_verdict, server_verdict, reason_codes }], recaptures_remaining: { [step]: number } } }`.
- `POST /v1/scans/:id/recapture` takes `{ steps: capture_step[], trigger_reason_code: string }`. It adds the next attempt per step. If any step would exceed attempt 3, that step becomes UNABLE_TO_ACQUIRE, the scan goes to `acquisition_failure` when the step is core (`neutral_face`, `fingertip_ppg`), and the response is 422 `DS_QG_099`.

- [ ] **Step 1:** Write tests:
  - `creates scan 201`
  - `same client_session_id returns 200 same id`
  - `second scan 20 min later → 409 DS_SCAN_001`
  - `scan captured 40 min later → 201`
  - `withdrawn consent offline → 451 DS_REG_001 and audit row capture_rejected_post_hoc`
  - `superseded → 451 DS_REG_002`
  - `recapture fingertip twice ok, third → 422 DS_QG_099 and status acquisition_failure`
  - `recapture only ocular step leaves face attempts unchanged`
- [ ] **Step 2:** Run. Expected: FAIL.
- [ ] **Step 3:** Implement.
- [ ] **Step 4:** Run. Expected: PASS.

### Task 6: Artefact multipart uploads and the quality trigger

**Files:** Create `backend/src/routes/artefacts.ts`, `backend/src/objectStore.ts` (`S3ObjectStore` + `FakeObjectStore`), `backend/test/api/artefacts.test.ts`

**Interfaces:**
- `ObjectStore`:
  - `{ createMultipart(key): Promise<string /*uploadId*/>; presignPart(key, uploadId, partNumber, ttlSec: 900): Promise<string>; completeMultipart(key, uploadId): Promise<void>; sha256(key): Promise<string> }`
  - `S3ObjectStore` uses the AWS SDK v3. The bucket and region come from env vars `S3_BUCKET` and `S3_REGION` (Malaysian region).
- `QualityQueue`: `{ enqueue(scanId: string): Promise<void> }`.
- Routes (user **or** device token):
  - `POST /v1/scans/:id/artefacts {step, attempt, kind, size_bytes, sha256}` → `{artefact_id, upload_id}`. The object key is `captures/{site_id}/{scan_id}/{step}/{attempt}/{kind}`, with no participant code in it.
  - `POST /v1/artefacts/:id/parts/:n/url` → `{url, expires_in: 900}`. `n` is 1–10000.
  - `POST /v1/artefacts/:id/complete` → `{status:'received_verified'}`, or 422 `DS_UPLOAD_001` with the artefact set to `rejected` on a sha256 mismatch.
- When every artefact for the latest attempt of each core step is `received_verified`, the scan moves to `quality_pending` and `qualityQueue.enqueue(scanId)` is called once.
- `POST /v1/scans/:id/features/extract` → 422 `DS_QG_000` unless the status is `quality_passed` (doc 04 §4.6).

### Task 8: Clinician review and experimental view audit

**Files:** Create `backend/src/routes/review.ts`, `backend/test/api/review.test.ts`

**Interfaces:**
- `AssertionVerifier`: `{ verify(userId: string, assertion: unknown, expectedChallengeHash: string): Promise<boolean> }`. The real implementation uses `@simplewebauthn/server` `verifyAuthenticationResponse`.
- `POST /v1/scans/:id/review` (`clinician` only) takes `{ action: 'confirm'|'flag'|'request_repeat'|'exclude', reason_code?, note?, webauthn_assertion }`. The challenge is the sha256 of the canonical JSON of `{scan_id, action, reason_code, note}`. A failed verify → 401 `DS_AUTH_003`.   - Every call with `enabled:true` writes a `view_experimental` audit row.
